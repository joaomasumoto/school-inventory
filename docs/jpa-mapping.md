# JPA — Persistence Mapping

[Back to project overview](../README.md) | [Domain model and decisions](domain-model.md)

## What is JPA?

JPA (Jakarta Persistence API) is a Java specification for object-relational persistence. It allows Java objects to be mapped to structures in a relational database.

In this project, Hibernate is used as the JPA implementation, while Spring Data JPA will provide abstractions to simplify data access.

Conceptually:

```text
Java Object <-> JPA / Hibernate <-> Relational Database
```

For example, an `Asset` object can be persisted as a row in the `assets` table.

## Asset Entity

The `Asset` class is mapped as a JPA entity:

```java
@Entity
@Table(name = "assets")
public class Asset {
    // Fields and constructors omitted.
}
```

- `@Entity` marks the class as a persistent JPA entity. Instances of `Asset` can be managed and persisted through JPA.
- `@Table(name = "assets")` defines the database table associated with the entity.

## Primary Key

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

`@Id` defines the entity's primary key. `@GeneratedValue` defines how the primary key is generated.

The current mapping uses `GenerationType.IDENTITY`, delegating ID generation to a database identity column. The ID is generated by the persistence/database layer instead of being provided when a new `Asset` is created. Using `Long` allows an unsaved asset's ID to remain `null`.

The project currently declares the PostgreSQL driver, not MySQL. PostgreSQL supports identity columns as well as sequences; `SEQUENCE` is therefore an available alternative. The current `IDENTITY` choice is not a limitation imposed by PostgreSQL.

### ID Naming

The current field has no explicit `@Column` name override and uses `id` under the default naming strategy. A name such as `id_asset` could be introduced as a project convention with `@Column(name = "id_asset")`, but that annotation is not part of the current implementation. Either name is technically valid.

## Required and Optional Fields

The database mapping follows the domain rules defined for an asset.

Required fields are:

- `name`
- `acquisitionMethod`
- `status`

These fields use `@Column(nullable = false)`.

Optional fields include:

- `entryDate`
- `notes`
- `assetNumber`
- `documentNumber`

For example, `entryDate` is optional because legacy assets may already exist in the school without a known entry date. This allows existing inventory data to be migrated without inventing unavailable information.

These annotations describe database mapping constraints; they do not validate constructor arguments. Null and blank validation in application code is still to be implemented. Database constraints also require a matching schema, managed through schema generation or migrations.

## Asset Name

```java
@Column(nullable = false, length = 50)
private String name;
```

The asset name is mandatory. Its maximum mapped length is 50 characters to maintain compatibility with the inventory spreadsheet format used by the school. Additional or longer descriptive information can be stored in `notes`.

The current `notes` field uses the default string mapping; no long-text column or custom length has been configured yet.

## Enum Persistence

The project contains domain enums such as `AssetStatus`, `AcquisitionMethod` and `MovementType`.

The currently mapped enums in `Asset` (`AssetStatus` and `AcquisitionMethod`) use `@Enumerated(EnumType.STRING)`. `MovementType` belongs to `AssetMovement`, whose persistence mapping has not yet been added.

```java
@Column(nullable = false)
@Enumerated(EnumType.STRING)
private AssetStatus status;
```

`STRING` stores the enum name itself in the database, for example:

```text
OPERATING
UNDER_MAINTENANCE
IDLE
UNUSABLE
```

This was preferred over `ORDINAL`, which would store the enum position (`0`, `1`, `2`, ...). Using `STRING` avoids coupling persisted data to the order in which enum constants are declared. Reordering constants therefore does not change the meaning of previously stored values. Renaming a constant still requires consideration of existing stored values.

## Asset Number and Uniqueness

The asset number (`assetNumber`) represents the identification number assigned to an individual asset by the municipality. It is optional because not every asset has an official asset number. However, when present, the value must be unique:

```java
@Column(unique = true)
private String assetNumber;
```

This represents the following domain rule:

> An asset may have no official asset number, but an existing asset number cannot identify more than one asset.

Absent asset numbers should be represented as `null`, rather than an empty string. Input normalization will be handled when the corresponding use cases are implemented.

The `documentNumber` is not unique because a single document, such as an invoice or delivery record, may contain multiple assets.

## JPA No-Argument Constructor

JPA entities require a public or protected no-argument constructor. Therefore, `Asset` contains:

```java
protected Asset() {
}
```

This constructor exists so that the JPA provider can instantiate the entity when reconstructing objects from persisted database records. It is different from the constructor used by the application:

```java
public Asset(
        String name,
        AcquisitionMethod acquisitionMethod,
        AssetStatus status) {
    this.name = name;
    this.acquisitionMethod = acquisitionMethod;
    this.status = status;
}
```

The public constructor expresses the intended domain rule for creating a new asset: an asset must have a name, acquisition method and status. It currently assigns these parameters without validating them.

The protected empty constructor exists for persistence purposes and is not intended to be the normal way application code creates assets. This preserves encapsulation while satisfying JPA requirements. Since the mapping annotations are placed on fields, JPA uses field access and does not require public setters.

## Current Mapping Decisions

- IDs are generated by the persistence/database layer.
- Required domain information is represented by non-nullable columns.
- Unknown legacy information may remain null.
- Mapped enums are persisted as strings rather than ordinal positions.
- Asset numbers are unique when present.
- Document numbers may be shared by multiple assets.
- Database constraints reflect rules already identified in the domain instead of defining arbitrary restrictions.
- JPA requirements should not weaken the domain model unnecessarily.

Only `Asset` is currently mapped as an entity. Database connectivity and schema setup are pending, so compilation alone does not verify persistence against a running database. As the project evolves, relationship mappings between `Asset`, `AssetMovement` and `Location` will be added.
